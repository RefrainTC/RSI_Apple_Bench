**Fixes made** (now in the card's "Acceptance fixes" section):
1. The 5090 card had no commands of its own. The general reproduce note targets the 4090 tasks; on the 5090 it named the wrong task and the wrong cache. A verified 5090 command block was added.
2. Environment scripts and wrappers hard-coded the authors' paths.
3. uv was not on PATH, and the authors had used uv 0.9.5 from an undocumented local install. The tester installed the same version into its own venv.
4. uv's default 30 s HTTP timeout failed once on the cuDNN wheel; `UV_HTTP_TIMEOUT=300` fixed it.
5. `uv python install` tries to write `~/.local/bin/python3.12`, outside the working directory. The card now suggests `--no-bin`.
6. The venv setup makes a CUDA call, so it must run under the GPU lock.

**Finding: an audit false positive.** A/A 2 was voided as `harness_fault`. In round 2 the baseline, on the 128/128 workload, returned one request as 128 tokens of pure whitespace, an honest temperature-1 output. The output check used `.strip()`, so it counted the answer as empty and flagged the baseline. One of four scorings was lost this way. Suggested fix: count only a truly empty string as empty, and rely on the re-tokenisation ratio check. The card carries this note; the harness is unchanged.

**Not tested:** the perturbed workload shapes.

**Against the write-up's claims** (authors' answer median 1.3633 over 5 runs, range 1.3548-1.3737; identity median 1.0021, range 0.9955-1.0053; sweep REF 1.6088, range 1.6009-1.6120; noise threshold ±0.02):
- The tester's median for the authors' answer is 1.3443, 1.4% low. All three runs fall below the authors' minimum, and 1.3327 is also outside ±0.02.
- The sweep configuration reads 3.1-3.8% low.
- Identity matches.
- All gates passed, and the 4 API-server processes were confirmed. Peak VRAM was at most 29,188 MiB, under the 30,720 MiB line.

**Likely cause: host load.** Per-burst times were compared with the authors' committed run files.

| | Tester vs authors |
|---|---|
| Baseline bursts | 3.5-6.4% faster |
| Authors'-answer bursts | 2.7-5.2% faster |
| Sweep configuration | −1.9% to +0.2% |
| 1-minute host load before each run | 1.4-1.9 (tester) vs 2.8-4.4 (authors) |

The baseline is bound by the CPU-side scheduler, so it gains the most from a quieter host, and the ratios shrink. REF therefore depends on host state. The qualitative result holds: the authors' answer sits about 0.34 above A/A.

**Setup:** a fresh shallow clone of Φ-Bench at commit 90d7251b; a no-cache image build in 1425 s; model download in 101 s (revision 989aa798, all 10 sha256 sums matched). The Dockerfile diff, the memory-utilization diff, the identity script and the 21 base sweep variants all regenerated byte-identical.

**Fixes made** (now in the workflow's "Acceptance fixes" section):
1. The Φ-Bench source was not in the repo and no URL was given. The URL (https://github.com/one2piece2hello/faibench_LLM_Infra_Bench) and the copy steps were added.
2. Every script hard-coded the authors' directory.
3. The model download script and the Dockerfile's download step fetched HEAD rather than a pinned revision. It matched on the test day.
4. The image's dependencies are unpinned: 6 of 161 packages differed from the authors' image record, including openai 3.58.0 and sentry-sdk 3.0.0.
5. On a host that already has the authors' image layers, a rebuild needs `--no-cache`; otherwise it silently reuses them.
6. The sweep's `--extra` JSON keys disagreed between the index (`base_seqs`/`base_tok`) and the variant generator (`seqs`/`tok`/`entry`).

**Not run:** the smoke, starter, negative, client-diagnostic and argument-check runs.
